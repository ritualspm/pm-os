# Idea to PRD

Take whatever text the user hands you — a Google Doc, a brief, a Slack thread, a back-of-napkin sketch typed up — and produce a tight Product Requirements Document.

## Input 

The text may be long, short, structured, or rambly. It may already contain partial sections. Treat it as raw material, not as a finished doc.

## Output format

A single markdown document. No preamble, no “here is your PRD” — the output **is** the PRD itself. Use these sections, in this order:

```
# <Title>

**Summary** — one sentence.

## Problem
What's broken or missing today. Concrete, not abstract.

## Target users
Who feels the problem. Roles or personas, not "everyone".

## Success metrics
How we'd know this worked. Measurable conditions where possible — counts, rates, percentages, time saved. If only directional metrics are knowable, say so.

## In scope
Bullet list of what this solves.

## Out of scope
Bullet list of adjacent things this deliberately does NOT solve.

## Non-goals
Bullet list of common asks that we are explicitly choosing not to do, and why.

## Open risks
Bullet list of what could go wrong, what's unknown, or where the input is sparse and assumptions had to be made.

## Context
Any setup details from the input that downstream steps need — project keys, repo names, ticket prefixes, deadlines, owners. Preserve verbatim. If none, omit this section.
```

## Tone and rigor

-   Founder-grade. Tight. No fluff, no padding to look thorough.
-   Concrete over abstract. Don’t write “improve user experience” when you can write “reduce time to first response from 24h to 1h”.
-   If the input is sparse, say so under **Open risks** rather than inventing detail. A short PRD with honest gaps beats a padded one with guesses.
-   No meta commentary (“This PRD was generated by…”, “Based on the input…”, etc.). Output is the PRD only.

## Length

Aim for 200–500 words of body content for a typical brief. Go longer only if the input genuinely warrants it.

Outcome

At the end, make sure that you as well , tone down your PRD as md file with proper name in the context of what you’ve received. Make the path and md file clear at the end.
